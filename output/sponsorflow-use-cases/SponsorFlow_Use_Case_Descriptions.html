SponsorFlow — Corrected Use Case Descriptions

The Use Case Diagram presents the interactions of five actors with SponsorFlow: Student Applicant, FASSG Personnel, Sponsor, Accounting Office Personnel, and System Administrator. Students register, request SLE-FHE verification, browse open programs, submit applications and documents, and monitor their status. FASSG manages programs and Fixed Lists, manually prepares Generated Batches, reviews member qualifications, submits the exact roster, records Sponsor decisions, and explicitly forwards eligible approved beneficiaries. Sponsors review submitted batches and approve or reject each entire batch. Accounting views and exports eligible forwarded beneficiary references without editing beneficiary records. The System Administrator manages accounts, audit-log access, and backup operations. Associations identify actor participation; include and extend relationships represent reused or conditional behavior rather than chronological handoffs.

Common interpretation

  • UC-01 to UC-22 retain the original numbering with corrected names and behavior. UC-23 to UC-26 add the missing request, member-review, receipt, and forwarding interactions.
  • An Active account is distinct from documented SLE-FHE verification. A Verified application is distinct from Sponsor approval.
  • Application statuses: Pending, Verified, Approved, Rejected, Ongoing, Expired, and Resubmission Requested. Batch membership is not a separate application status.
  • Generated Batch statuses: Saved, Submitted, Approved, and Rejected. FASSG receipt and Accounting forwarding are separate recorded actions, not additional batch-status labels.
  • A Saved batch may contain ordinary Pending/Verified applicants, the complete explicitly selected finalized Fixed List roster, or both. Draft creation and source-list finalization do not consume slots.
  • Fixed List members need no separate online application. Internal processing records preserve source provenance and do not manufacture grades, documents, or verification.
  • Authentication is a precondition for protected functions. Includes/extends do not represent the chronological Sponsor-to-FASSG-to-Accounting handoff.
  • For Accounting, read-only means beneficiary and approval records cannot be edited; an authorized export may still create an audit entry.

Table 3.24: Login / Authenticate

FieldContent
Use case ID

UC-01

Use case name

Login / Authenticate

Primary actor

All five user roles

Secondary actor

None

Description

Authenticates an active user and opens the dashboard assigned to the user's role.

Preconditions

The user has an existing active account and is not currently authenticated.

Trigger

The user opens the login page and submits credentials.

Main flow

1. The system displays the email and password fields.

2. The user enters their email and password and submits the form.

3. The system validates the credentials and account status.

4. The system regenerates the session and determines the user's role.

5. The system redirects the user to the Student, FASSG, Sponsor, Accounting, or Administrator dashboard.

Alternative flows

1. The user selects Remember me to request persistent authentication.

Exception flows

1. Invalid credentials or an inactive account prevent authentication and produce a validation message.

2. A credential-verification failure returns an error without granting access.

Postconditions

An authenticated session exists with role-restricted access. No SLE-FHE verification or sponsorship decision is created.

Includes / extends

None. Authentication is a precondition for protected use cases, not a login interaction repeated within each use case.

Use case name

Register Student Account

Primary actor

Student Applicant

Secondary actor

None

Description

Creates a student account and profile using validated identity information and the official academic-program catalog.

Preconditions

The student does not already have an account using the submitted institutional email or Student ID.

Trigger

The student opens the registration form.

Main flow

1. The system displays the registration form and active undergraduate academic programs.

Exception flows

1. Duplicate identifiers, invalid fields, missing consent, or an inactive, postgraduate, or nonexistent program prevent registration.

Postconditions

The account and profile exist. The student remains unverified for SLE-FHE until FASSG separately records legitimate verification.

None. UC-01 is a subsequent action, not an included automatic login.

UC-04

Use case name

Submit Sponsorship Application

Primary actor

Student Applicant

Secondary actor

None; FASSG reviews the stored application in a later interaction.

Description

Submits an ordinary student application and applicable supporting evidence for an open program.

Preconditions

The student is authenticated, has documented SLE-FHE verification, satisfies applicable program checks, has no conflicting active sponsorship, and is not barred by an existing application or prior rejection for the same program. The application period is open.

The student selects Apply for an open program.

Includes / extends

Included by UC-05. Extended by UC-10 at Attach supporting documents when documents are required or supplied. No student application Save as draft feature is represented.

Table 3.31: Verify SLE-FHE Eligibility

FieldContent
Use case ID

UC-08

Use case name

Verify SLE-FHE Eligibility

Primary actor

FASSG Personnel

Secondary actor

None; the student's request is submitted separately through UC-23.

Description

Records a genuine FASSG decision on a pending SLE-FHE verification request using identity, registry, and office evidence.

Preconditions

FASSG is authenticated. A matching submitted pending request and complete student identity/address information exist. Existing verification evidence must not be overwritten.

Trigger

FASSG selects a pending SLE-FHE request for review.

Main flow

1. The system displays the request, student identity, address information, and institutional registry comparison.

2. FASSG examines the evidence and explicitly confirms the student's identity.

3. FASSG submits the verification decision for the selected request.

4. The system validates the request and supporting match or authorized evidence-based override.

5. The system records the verifying officer, timestamp, and verified address; marks the request verified; and records the audit evidence.

6. The system makes the verification result available to the student.

Alternative flows

1. FASSG returns a pending request for correction with a reason, preserving its evidence.

2. A registry mismatch requires an explicit FASSG override, a reason, and a traceable office-evidence reference; matching alone is not an automatic verification decision.

Exception flows

1. No matching pending request, incomplete identity/address, missing override evidence, or an existing verification record prevents an unsupported overwrite or verification.

Postconditions

A documented verification decision exists. No application is automatically approved, and no batch is automatically submitted.

Includes / extends

None. UC-23 precedes this interaction. Program-specific member verification is UC-24.

Use case name

Encode / Import Sponsor Fixed List

Primary actor

FASSG Personnel

Secondary actor

None; the Sponsor is the originator of the list supplied to FASSG.

Description

Records a Sponsor-provided candidate list as an editable Fixed List for a specific program.

Preconditions

FASSG is authenticated, the program exists, and the source list is available. Editing requires a Draft list.

Trigger

FASSG creates a Fixed List or opens its manual encoding/import controls.

Main flow

1. FASSG identifies the program and source list details.

2. FASSG manually encodes candidates or uploads the supported CSV/Excel source.

3. The system validates the submitted/imported candidate information and source association.

4. The system saves candidate entries and displays their current review states.

1. Invalid data, source discrepancies, a protected historical reference, or a finalized list blocks the affected operation.

2. A candidate without documented SLE-FHE verification cannot be treated as verified through list encoding.

Postconditions

The Draft Fixed List contains candidate-source records. No sponsorship slots are reserved or consumed, and no separate online application is demanded from a Fixed List candidate.

Includes / extends

None. UC-12 is a later explicit action, not a mandatory part of every encoding/import operation.

Use case name

Finalize Fixed List

Primary actor

FASSG Personnel

Secondary actor

None

Description

Locks a reviewed Sponsor-provided source list so FASSG can deliberately use it in Generated Batch preparation.

Preconditions

FASSG is authenticated. A nonempty editable Draft Fixed List exists for the program, with documented verification and recorded endorsements for its members.

Includes / extends

None. A finalized list may later be explicitly selected in UC-13.

Table 3.36: Manually Prepare Generated Batch

FieldContent
Use case ID

UC-13

Use case name

Manually Prepare Generated Batch

Primary actor

FASSG Personnel

Secondary actor

None

Description

Creates or safely edits an unsubmitted program batch using explicitly selected ordinary applicants, a finalized Fixed List roster, or both.

Preconditions

FASSG is authenticated. The target program is open and unexpired. Candidates have documented SLE-FHE verification and no conflicting active sponsorship. Ordinary applications are Pending or Verified; a selected source list is Finalized and belongs to the same program.

Trigger

FASSG opens Create Batch or a permitted draft-batch preparation action.

Main flow

1. FASSG selects the program and batch details.

2. FASSG manually checks ordinary applicants and/or deliberately selects a finalized Fixed List.

3. For a selected Fixed List, the server retrieves its complete stored roster; it does not trust client-supplied member names.

4. The system checks source membership, candidate identity, verification/endorsement prerequisites, existing batch assignments, duplicate membership, and capacity.

5. The system saves the exact selected members with source references in a Saved Generated Batch.

6. FASSG opens that draft for the separate member review and submission actions.

Alternative flows

1. The batch contains only ordinary applicants, only Fixed List candidates, or a combination.

2. The same student selected through both sources is represented once with the retained Fixed List source link; duplicate source identities or conflicting records require review.

3. FASSG may remove an individual member from an eligible unsubmitted draft without deleting the original source-list entry.

Exception flows

1. Zero selection, invalid source/program association, missing prerequisite evidence, conflicting membership, or excessive capacity blocks preparation without silently dropping members.

Postconditions

A Saved batch exists with unique membership and source provenance. Rank positions remain unset. Draft creation neither marks Pending members Verified nor grants approval or consumes slots.

Includes / extends

None. UC-24 and UC-14 are separate subsequent actions; they are not executed automatically during draft creation.

Table 3.37: Submit Batch to Sponsor

FieldContent
Use case ID

UC-14

Use case name

Submit Batch to Sponsor

Primary actor

FASSG Personnel

Secondary actor

None; the assigned Sponsor reviews the result later through UC-15.

Description

Submits the complete verified program roster to the assigned Sponsor and freezes its membership for review.

Preconditions

FASSG is authenticated. A permitted batch exists, each member has completed required verification, and the roster satisfies eligibility, evidence, identity, and capacity rules.

Trigger

FASSG selects Submit to Sponsor on the Generated Batch.

Main flow

1. FASSG reviews the complete roster and submits it.

2. The system locks the program, batch, and relevant records for consistency checks.

3. The system validates every member, applicable documents and qualifications, conflicts, and current capacity.

4. The system records or verifies the exact roster snapshot and its program/Sponsor association.

5. The system sets Submitted, advances the submission version, and records the submission audit event.

6. The submitted batch becomes available to the assigned Sponsor.

Alternative flows

1. A rejected batch may be resubmitted only after FASSG records receipt of the rejection, the original roster remains intact, and current checks pass.

Exception flows

1. An unverified/ineligible member, missing evidence, over-capacity selection, stale state, or changed frozen roster blocks the entire submission.

Postconditions

The exact roster is Submitted and protected against unauthorized membership changes. No Sponsor approval or slot consumption occurs at submission.

Includes / extends

None. Completed verification is a precondition; submission does not automatically perform FASSG's human review. No automatic Sponsor email is claimed.

Table 3.39: Approve or Reject Entire Submitted Batch

FieldContent
Use case ID

UC-16

Use case name

Approve or Reject Entire Submitted Batch

Primary actor

Sponsor

Secondary actor

None; FASSG receives and records the decision through UC-25.

Description

Records an explicit Sponsor decision on the entire unchanged submitted roster.

Preconditions

The Sponsor is authenticated and assigned to the program. The current submission is actionable and its roster is intact. Approval additionally requires current uploaded confirmation evidence and all member/capacity checks to pass.

Trigger

The Sponsor explicitly selects Approve Entire Batch or Reject Entire Batch.

Main flow

1. The Sponsor reviews the current whole batch and chooses approval.

2. The system validates authorization, submission version, exact membership, and the current uploaded confirmation evidence.

3. Within the controlled transaction, the system checks all members' qualifications, documents, verification, active-sponsorship conflicts, and available capacity.

4. The system approves the complete batch, records the Sponsor and decision time, and updates the applicable individual beneficiary and active-sponsorship records.

5. The system records the audit evidence and sends the implemented application-approval notifications.

Alternative flows

1. For whole-batch rejection, the system records a separate rejection decision and marks the batch Rejected. Existing uploaded evidence and application qualification history are preserved. No individual replacement, re-ranking, or mass application rejection occurs.

Exception flows

1. Stale submission/evidence, unauthorized access, an invalid member, conflicting active sponsorship, or insufficient capacity prevents approval without partial beneficiary updates.

2. Standalone individual Sponsor approval/rejection operations are blocked.

Postconditions

The batch is Approved or Rejected with a recorded Sponsor decision. Approved batches await FASSG receipt and forwarding; Accounting access is not automatically granted.

Includes / extends

None. UC-17 supplies evidence before approval. UC-25 and UC-26 are separately initiated FASSG actions, not included Sponsor actions.
